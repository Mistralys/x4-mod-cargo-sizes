# WP-001: Replace Hardcoded Backend Data with Real x4-core Values

## Overview

Replace all hardcoded placeholder physics values in `PhysicsService` and `ShipDataService` with real per-ship data from x4-core v1.3.0's `ShipDef` and `EngineDef` APIs. Extend the relevant DTOs to carry real data and absolute metrics. This is the foundational work package — all subsequent work packages depend on it.

## Plan Reference

**Plan Steps:** 1–9 (Phase 1)

## Description

The existing backend uses hardcoded placeholder values:
- `PhysicsService` creates `Drag(100, 100, 100, 100, 100, 100, 100)`, `Inertia(10, 10, 10)`, and `Jerk(50, ...)` — all percentage changes displayed are meaningless percentages of arbitrary numbers.
- `ShipDataService.getShipCargoCapacity()` returns hardcoded estimates (e.g., L=30000) instead of real per-ship values.
- `ShipDataService.loadAllEngines()` estimates reverse/boost/travel thrust as multipliers of forward thrust instead of using real `EngineDef` getters.

This WP replaces all of these with real data from x4-core v1.3.0.

## Requirements

### Step 1: Modify `PhysicsService.calculatePhysics()`
- Accept real per-ship drag, inertia, and jerk values from `ShipDef` instead of creating hardcoded objects.
- When an optional `shipId` is present in the request, load real physics data from `ShipDef`.
- When `shipId` is absent (manual input mode), fall back to current behavior.

### Step 2: Modify `PhysicsService.calculateEnginePerformance()`
- Accept engine count from `ShipDef.countEngines()`.
- Formula: `totalThrust = thrustForward * engineCount`.
- Add top speed calculation: `topSpeed = (thrustForward * engineCount * 1000) / dragForward`.
- Add `engineCount` parameter (default: 1 for backward compatibility).

### Step 3: Modify `ShipDataService.getShipCargoCapacity()`
- Use `ShipDef.getCargoCapacity()` instead of the hardcoded `match($size)` fallback.
- Fall back to hardcoded estimates only when `getCargoCapacity()` returns 0.

### Step 4: Modify `ShipDataService.loadAllEngines()`
- Use real `EngineDef` getters: `getThrustReverse()`, `getBoostThrust()`, `getTravelThrust()`.
- Replace estimated multipliers (`thrustForward * 0.5`, `* 2.0`, `* 4.0`) with real values.

### Step 5: Update `ShipDataService.getShipDetails()`
- Include engine count from `ShipDef.countEngines()` in the `ShipDetails` DTO.
- Add `engineCount` field to the DTO.

### Step 6: Extend `PhysicsRequest` DTO
- Add optional `?string $shipId` field.
- Update `fromArray()` to parse the new field.
- When present, `PhysicsService` loads the ship's real physics data.

### Step 7: Extend `PhysicsResponse` DTO
- Add absolute metrics: `topSpeed` (m/s, original and adjusted, null if no engine), `acceleration` (m/s², original and adjusted, null if no engine).
- Add these fields to `toArray()`.

### Step 8: Extend `EnginePerformance` DTO
- Add `topSpeed` (original and adjusted), `topSpeedReverse`, `topSpeedBoost`, `topSpeedTravel`.
- Add engine count used.

### Step 9: Update `ShipDetails` DTO
- Add `engineCount: int`.
- Add real drag/inertia/jerk values as nested arrays.
- Add cargo type.

## Technical Constraints

- **Synchronous file I/O only** — all backend operations use synchronous PHP functions.
- **PHP strict types** — every modified PHP file must have `declare(strict_types=1)`.
- **Readonly DTOs** — all new DTO properties must be `readonly`.
- **PSR-12 coding standard** — PHP code follows PSR-12.
- **Backward compatibility** — all new fields are optional/nullable to avoid breaking existing API consumers; existing fields remain unchanged.
- **No new dependencies** — use only existing Composer packages.

## Acceptance Criteria

1. `PhysicsService` uses real per-ship drag, inertia, and jerk values from `ShipDef` when a `shipId` is provided — no more hardcoded `Drag(100,...)`, `Inertia(10,...)`, `Jerk(50,...)`.
2. `ShipDataService.loadAllEngines()` returns real reverse/boost/travel thrust values from `EngineDef`, not estimated multipliers.
3. `ShipDataService.getShipCargoCapacity()` returns `ShipDef.getCargoCapacity()` for ships where it's available (>0).
4. `PhysicsResponse` includes `topSpeed` and `acceleration` fields (original and adjusted, null when no engine selected).
5. `EnginePerformance` DTO includes `topSpeed`, `topSpeedReverse`, `topSpeedBoost`, `topSpeedTravel`, and engine count.
6. `ShipDetails` DTO includes `engineCount`, real drag/inertia/jerk values, and `cargoType`.
7. `PhysicsRequest` accepts an optional `shipId` parameter.
8. All existing API behavior continues to work when `shipId` is not provided (backward compatibility).
9. No new Composer dependencies added.
10. All new DTO properties are `readonly`.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| `ShipDef.getCargoCapacity()` returns 0 for many ships | Fall back to size-based estimates only when value is 0 |
| Engine count varies per ship, affecting top speed accuracy | Use `ShipDef.countEngines()` for per-ship count; label as "estimated" |
| Breaking change in `PhysicsResponse` format | Add new fields as optional/nullable; existing fields unchanged |
