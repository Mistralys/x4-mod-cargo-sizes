# Synthesis: Shared Ship Types Config

**Date:** 2026-11-22 | **Status:** COMPLETE (4/4 WPs, all pipeline stages PASS)

### Outcome Summary

Ship type definitions (keyword matching, keyword aliases, display labels) that were duplicated between the CLI CargoSizeExtractor and the GUI ShipDataService now live in a single config/ship-types.json, read through a new shared ShipTypeConfig class, with sizes as the ShipTypeConfig::SIZES constant. Both layers delegate to it and the hardcoded scavenger/terraformer checks are gone, while the CLI build output stayed identical to the pre-change baseline apart from the version, build date and random example ships. The GUI now lists storage ships under Transport, an intended behaviour change, and the baseline parity check was done by manual normalisation rather than a repeatable script.

### Strategic Recommendations

- A new ship class is now a one-line JSON edit picked up by both layers; the "same logic as CLI" contract no longer needs enforcement.
- Explicit, validated `primaryKeyword` makes the CLI output contract independent of array order.
- Line endings are a build-output risk: earlier WPs saved LF into a CRLF tree, which changed embedded multi-line strings in `_readme.txt`, `info.xml` and `ModuleConfig.xml`. It was caught only because of the byte-level baseline comparison. Keep that oracle for future refactors and normalise line endings.
- Build-parity checking needed manual normalisation (version, build date, random example ships, baseline listing format). A repeatable script would make the gate reliable.
- The baseline lacked CRCs, so size-only zip comparison is a weak byte-identity oracle.
